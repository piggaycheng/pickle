## Problem Statement

Build a local-first tool that takes pickleball match videos, initially from YouTube, and helps create per-player action timelines. The first useful output is:

- A human-readable timeline: `timestamp`, `player`, `action`
- A training dataset: video clips, annotations, player identity, pose/bbox metadata, and model confidence

The system is for personal use first, but should keep a path toward becoming a more general commercial product later.

## What Makes This Useful

The core value is not that the first model is perfect. The value is that every correction becomes training data. The tool should reduce manual labeling time now and steadily improve toward automatic labeling later.

## Constraints

- Source videos are usually YouTube match videos.
- Videos may include cuts, audience shots, replay segments, overlays, zooms, and changing camera angles.
- The ball may not be visible or reliable enough to depend on.
- Both singles and doubles should be supported eventually.
- Initial user tolerance: manual setup and correction are acceptable.
- Long-term goal: only early-stage/manual correction, then increasingly automatic annotation.
- Project currently uses Python with `uv`, OpenCV, MediaPipe, and yt-dlp.

## Premises

1. The first version should be a semi-automatic annotation system, not a fully automatic classifier.
2. Early manual player identity confirmation is required, but the user should not manually label every segment.
3. Action recognition should begin with hit-event candidates, then classify actions around those events.
4. MediaPipe pose is useful but insufficient alone. The system also needs player boxes, motion features, court position, and optional ball cues.
5. YOLO-style detection can find people, but same-player identity across time requires tracking and later re-identification.
6. The annotation format must be designed from day one so corrected labels become usable training data.

## Recommended Approach

Use an annotation-engine-first MVP with model-assisted suggestions.

The product is not "a Streamlit app." The product is a replayable annotation engine:

```text
video
  -> segment
    -> player track
      -> identity session
        -> hit event candidate
          -> action annotation
            -> correction history
              -> dataset export
```

Streamlit is only the first UI over this engine. The data model and artifacts must remain portable if the UI later moves to a custom frontend, desktop app, or hosted product.

Recommended first implementation: a local Streamlit app backed by plain JSON/JSONL files.

Why:
- Streamlit is fast enough for a personal annotation tool.
- It keeps the first version inside the existing Python/uv project.
- It avoids frontend build complexity while the data model is still changing.
- The dataset format remains portable if the UI later moves to a custom web app.

The first system should prioritize a fast correction loop:

1. Import a YouTube or local video.
2. Create players: `A`, `B`, `C`, `D`.
3. Detect candidate people and pose landmarks.
4. Ask the user to assign visible players at the start of a rally or when identity confidence is low.
5. Generate candidate hit-event timestamps.
6. Let the user quickly confirm or edit `player`, `timestamp`, and `action`.
7. Export both a readable timeline and structured training data.

## Slice Roadmap

The MVP should advance through small vertical slices. Each slice must preserve the artifact/state split, keep generated paths inside the project data root, and pass `uv run pytest` before the next slice starts.

### Slice 1: Schema, Storage, Jobs

Status: DONE.

Purpose: establish strict project contracts before adding computer vision or UI behavior.

Scope:

- `pickleball_ai/schema.py`: strict Pydantic models, enums, schema versions, and core invariants.
- `pickleball_ai/storage.py`: safe project paths, project layout creation, JSON/JSONL IO, and atomic writes.
- `pickleball_ai/jobs.py`: replayable processing job lifecycle and artifact manifests.
- Tests for schema validation, path safety, storage behavior, and job transitions.

### Slice 2: Replayable Pose Extraction

Status: DONE.

Purpose: convert the prototype MediaPipe script into a replayable job that writes portable artifacts.

Scope:

- `pickleball_ai/pose.py`: frame source abstraction, MediaPipe detector wrapper, pose frame serialization, and pose extraction job.
- `pose_detector.py`: thin CLI wrapper that creates/uses a project and runs pose extraction.
- Output: `artifacts/jobs/{job_id}/pose.jsonl`.
- Tests with fake frame sources and fake detectors.
- Smoke test with a short local clip before using full match videos.

### Slice 3: Annotation and Coverage Core

Status: DONE.

Purpose: create the source of truth for human labels and reviewed/unreviewed video coverage before building queue or UI features.

Scope:

- `pickleball_ai/annotations.py`: append-only annotation events, current annotation projection, correction provenance, and validation.
- `pickleball_ai/coverage.py`: coverage events and latest-state projection.
- Support coverage states: `unreviewed`, `reviewed`, `skipped_non_game`, and `needs_recheck`.
- Outputs:
  - `state/annotation_events.jsonl`
  - `state/annotations.jsonl`
  - `state/coverage_events.jsonl`
  - `state/coverage.jsonl`
- Tests for event projection, invalid time windows, overlap handling, latest-state wins, and the rule that unreviewed time is not treated as negative training data.

### Slice 4: Player and Identity Session Core

Status: DONE.

Purpose: separate visual tracks from player identity so YouTube cuts, replays, and camera changes can be corrected without corrupting labels.

Scope:

- `pickleball_ai/players.py`: player definitions such as `A`, `B`, `C`, `D`.
- `pickleball_ai/identity.py`: identity-session events that map a track or manual selection to a player over a time window.
- Outputs:
  - `state/players.json`
  - `state/identity_sessions.jsonl`
  - `state/tracks.jsonl` only when track data exists
- Tests for overlapping identity sessions, cut/replay invalidation, missing identity, and annotation references to players.

### Slice 5: Hit Candidate Generation

Status: DONE.

Purpose: generate reviewable hit-event candidates from pose data without pretending they are final labels.

Scope:

- `pickleball_ai/events.py`: pose-motion heuristics over `pose.jsonl`.
- Candidate features may include wrist acceleration, shoulder/hip rotation, player movement peaks, and nearby pose confidence.
- Output: `artifacts/jobs/{job_id}/hit_candidates.jsonl`.
- Candidate records must include confidence, source artifact refs, and enough debug features to explain why the candidate exists.
- Tests using synthetic pose frames for peak clustering, threshold behavior, missing landmarks, and duplicate suppression.

### Slice 6: Review Queue

Status: DONE.

Purpose: turn suggestions, coverage gaps, and identity uncertainty into an actionable worklist while keeping the queue out of the source-of-truth path.

Scope:

- `pickleball_ai/queue.py`: materialize review tasks from hit candidates, low identity confidence, coverage gaps, and stale suggestions.
- Queue statuses: `open`, `accepted`, `corrected`, `dismissed`, and `stale`.
- Output: `state/review_queue.jsonl`.
- Queue rebuilds must be idempotent and able to mark stale tasks when upstream artifacts change.
- Tests for rebuild idempotency, stale handling, task priority, and the rule that annotations/coverage remain source of truth.

### Slice 7: Metrics and Project Summary

Status: DONE.

Purpose: make project quality visible before scaling annotation volume or training models.

Scope:

- `pickleball_ai/metrics.py`: reviewed duration, skipped duration, unreviewed duration, annotations per reviewed minute, identity correction counts, and action correction counts.
- `pickleball_ai/summary.py`: project-level debug report that lists videos, jobs, artifacts, failures, queue counts, and coverage status.
- Outputs:
  - `state/metrics.json`
  - `state/project_summary.json`
- Tests for zero-denominator metrics, unavailable-vs-zero values, reviewed-only denominators, failed job summaries, and artifact counts.

### Slice 8: Minimal Streamlit Annotation Workspace

Purpose: add a usable local UI over the stable annotation engine without putting business logic inside Streamlit reruns.

Scope:

- `pickleball_ai/ui_streamlit.py` or a small `streamlit_app.py` entrypoint.
- Three-pane workspace:
  - video/player view
  - queue and annotation inspector
  - timeline and coverage map
- Keyboard-first controls for accept, correct, dismiss, seek next/previous, and mark coverage.
- UI reads and writes through annotation, coverage, identity, and queue modules only.
- Heavy processing jobs must run outside the Streamlit render loop.
- Tests should cover pure state helpers; UI behavior can be smoke-tested manually first.

### Slice 9: Dataset Export and Model Iteration

Purpose: turn corrected annotations into training data only after enough trusted labels exist.

Scope:

- Export readable timelines and structured training datasets.
- Clip extraction around accepted annotations.
- Model suggestion isolation: model outputs remain suggestions until accepted or corrected.
- Reserve `source_tool` and `external_refs` for future CVAT interoperability, but keep the full CVAT converter deferred.
- Add evaluation harnesses for candidate/event/model versions once annotation volume is meaningful.

## Approaches Considered

### Approach A: Annotation-First MVP

Summary: Build the timeline annotation tool first. Detection and pose models only provide suggestions. User corrections are first-class data.

Effort: Medium
Risk: Low

Pros:
- Fastest path to a usable personal tool.
- Handles model mistakes because correction is built into the workflow.
- Creates the dataset needed for future transfer learning.
- Does not require stable ball tracking in the first version.

Cons:
- Initial workflow is not fully automatic.
- Accuracy depends on user correction volume.
- Tracking and classification quality improve only after enough labeled examples exist.

### Approach B: Tracking and Event Detection Core

Summary: Build player detection, tracking, rally segmentation, and hit-event detection before building the annotation interface.

Effort: Large
Risk: Medium

Pros:
- More similar to a future product architecture.
- Better long-term foundation for full automation.
- Clean separation between video processing and annotation UI.

Cons:
- Slower to reach a usable personal workflow.
- YouTube cuts and non-court shots make tracking hard early.
- Delays dataset creation, which is the real bottleneck.

### Approach C: Model-First Experiment

Summary: Collect labeled clips manually and train an action classifier early to test whether action categories are separable.

Effort: Medium to Large
Risk: High

Pros:
- Quickly validates whether labels like drive, slice, volley, dink, and lob are visually separable.
- Helps discover which features matter.

Cons:
- Without a labeling tool, training data quality will be inconsistent.
- The model may learn camera angle, player identity, or video style instead of action mechanics.
- Does not solve the time-saving workflow problem.

Coverage events are append-only. Latest event wins when resolving overlapping ranges.


Rules:

- Metrics count recall only over reviewed ranges.
- Skipped non-game ranges are excluded from denominators.
- Annotations are allowed only in reviewed or needs-recheck ranges unless explicitly marked as draft.
- Overlapping coverage events resolve by latest event, while history remains append-only.

## Initial Action Labels

Start small. Too many labels will make the dataset noisy.

Recommended first label set:

- `drive`: flat or topspin attacking shot
- `slice`: underspin or cut shot
- `volley`: hit before bounce near or inside transition zone
- `dink`: soft kitchen shot
- `lob`: high defensive or attacking lift
- `serve`: serve motion
- `unknown_hit`: hit event exists, action unclear
- `not_hit`: false positive event

Defer labels like reset, block, speed-up, drop, overhead, and third-shot drop until the basic workflow is stable.

## Pipeline

### Phase 1: Ingest

- Download YouTube video using `yt-dlp`.
- Store original video under `videos/{video_id}/source.mp4`.
- Extract metadata: fps, resolution, duration.
- Optionally create a lower-resolution proxy for fast UI scrubbing.
- Use internal `video_id` for paths. External titles are metadata only.
- Reject unsupported URL/source types loudly.
- Keep all outputs inside the project data directory.

### Phase 2: Scene and Rally Filtering

Goal: remove obvious non-game footage before player analysis.

First version:
- Detect hard cuts using frame histogram difference.
- Mark segments with too many faces/audience-like people as `non_court_candidate`.
- Let the user include/exclude segments manually.

Later:
- Train a court/rally classifier.
- Detect court lines or court region for more reliable filtering.

### Phase 3: Player Detection and Pose

First version:
- Use MediaPipe pose on sampled frames.
- Keep existing `pose_detector.py` as the starting point, but refactor output from rendered video only into structured pose JSON.

Near-term upgrade:
- Add person detection with YOLO or RT-DETR.
- Use pose only inside person bounding boxes where possible.

### Phase 4: Player Identity

First version:
- User assigns `Player A/B/C/D` to tracks at the beginning of useful segments.
- System carries identity forward until confidence drops.
- If a cut happens, the system asks for confirmation again.

Later:
- Add tracker such as ByteTrack or DeepSORT.
- Add visual re-identification using color histograms or embeddings.
- Store identity confidence and never silently overwrite manual labels.

### Phase 5: Hit-Event Candidates

First version:
- Generate candidate timestamps from pose/motion heuristics:
  - wrist acceleration peaks
  - shoulder/hip rotation changes
  - paddle-side arm velocity
  - player deceleration or footwork pause around contact
- Cluster nearby peaks so the UI shows events, not noisy per-frame detections.

Important: if the ball is visible, use it as an optional feature. Do not make it required.

### Phase 6: Action Annotation UI

The minimum useful UI needs:

- Video player with keyboard scrubbing.
- Timeline with suggested hit events.
- Player selector: `A`, `B`, `C`, `D`.
- Action hotkeys: drive, slice, volley, dink, lob, serve, unknown, not-hit.
- Low-confidence identity checkpoints.
- Export button for timeline and dataset.

The UI can be local-only at first. A simple Streamlit, Gradio, or small web app is enough. The key is annotation speed.

Recommended MVP UI layout:

```text
+-------------------------------------------------------------+
| Video Player                                                |
| segment, overlays, timestamp, playback controls             |
+---------------------------+---------------------------------+
| Review Queue              | Annotation Inspector            |
| hit candidate             | player                          |
| identity check            | action label                    |
| coverage gap              | time window / timing confidence |
| stale item                | source / correction history     |
+---------------------------+---------------------------------+
| Full Timeline + Coverage Map                                |
| reviewed / skipped / needs_recheck / unreviewed             |
+-------------------------------------------------------------+
```

Initial keyboard shortcuts:

```text
Space: play/pause
J/K/L or arrows: scrub
1-4: Player A-D
D/S/V/K/L/O/U/N: action labels
Enter: accept current item
Backspace: undo last annotation event
R: mark range reviewed
X: skip non-game range
F: jump to full timeline
Q: jump back to queue
```

The review queue accelerates work. The full timeline and coverage map prevent silent missed clips.

Split stored data into immutable artifacts, mutable state, append-only event logs, and materialized views.

```text

   |
   v
processing_jobs.jsonl
   |
   +--> artifacts/jobs/{job_id}/pose.jsonl
   +--> artifacts/jobs/{job_id}/hit_candidates.jsonl
   +--> artifacts/jobs/{job_id}/segments.jsonl
   +--> artifacts/jobs/{job_id}/suggestions.jsonl
   |
   v
project_state/
   +--> players.json
   +--> tracks.jsonl
   +--> identity_sessions.jsonl
   +--> annotations.jsonl
   +--> annotation_events.jsonl
   +--> coverage.jsonl
   +--> review_queue.jsonl
   +--> metrics.json
   +--> project_summary.json
```

Slice 1 implementation should use this concrete on-disk layout:

```text
datasets/{project_id}/
  project.json
  video.json
  processing_jobs.jsonl
  videos/source.mp4
  artifacts/jobs/{job_id}/manifest.json
  state/
  exports/
```

Rules:

- Raw video and job artifacts are immutable.
- Human-approved annotation state is mutable only through append-only annotation events.
- Review queue is rebuildable from artifacts and project state.
- Model suggestions never overwrite human-approved annotations.
- Exports should create a new versioned file instead of overwriting prior exports.

JSON/JSONL IO rules for Slice 1:

- Single JSON files are written via temp file, flush, then replace target.
- JSONL append writes one compact JSON object plus newline.
- Empty JSONL files are valid.
- Malformed JSONL lines raise an error with the line number.
- Malformed lines must not be silently skipped.
- Multi-process concurrent writes are not supported in Slice 1.

## Error & Rescue Registry

| Codepath | What Can Go Wrong | Error Type | Rescue Action | User Sees |
|---|---|---|---|---|
| YouTube ingest | URL invalid or unsupported | `InvalidSourceError` | Reject before job starts | "Use a supported YouTube URL or local file." |
| YouTube ingest | Download fails | `VideoDownloadError` | Mark job failed, keep prior data | "Download failed. Retry or choose another source." |
| Metadata extraction | OpenCV cannot open video | `VideoOpenError` | Mark job failed | "Video could not be opened." |
| Metadata extraction | FPS or duration missing | `VideoMetadataError` | Use fallback only if explicit, otherwise fail | "Video metadata is invalid." |
| Pose extraction | MediaPipe model missing | `ModelAssetError` | Attempt download or ask user to install | "Pose model is missing." |
| Pose extraction | Frame decode fails | `FrameDecodeError` | Skip frame if isolated, fail if repeated | "Some frames could not be processed." |
| Pose extraction | Out of memory | `ProcessingMemoryError` | Fail job, suggest lower resolution/proxy | "Video is too large for current settings." |
| Segment detection | Empty segment output | `EmptySegmentError` | Mark all as unreviewed fallback | "No game segments were detected." |
| Hit candidates | Candidate count explodes | `CandidateOverflowError` | Cap and mark job needs review | "Too many candidate events. Adjust thresholds." |
| Annotation save | Schema invalid | `SchemaValidationError` | Reject write | "Annotation is invalid and was not saved." |
| Annotation save | JSONL write interrupted | `ArtifactWriteError` | Write temp then atomic replace where possible | "Save failed. Retry." |
| Coverage update | Overlapping range conflict | `CoverageConflictError` | Resolve by latest event and log supersede | "Coverage updated; prior range superseded." |
| Metrics generation | Denominator is zero | `MetricsUnavailableError` | Emit unavailable metric, not zero | "Metrics unavailable until reviewed ranges exist." |

Failure state is part of the job record. Errors must not be print-only.

## Security and Data Safety

- Do not use external video titles as primary keys or path roots.
- Restrict all generated files to the project data directory.
- Validate all imported JSON/JSONL against schema before writing state.
- Dry-run external imports before applying them.
- Do not allow UI actions to overwrite immutable artifacts.
- Require confirmation for destructive actions.
- Preserve prior exports by writing versioned output files.

## Transfer Learning Strategy

Do not start with transfer learning. Start by building clean labels.

Once there are enough labeled examples:

1. Train a baseline classifier on pose and motion features.
2. Compare it against a video model using short clips around hit events.
3. Fine-tune only after the dataset has enough variation in:
   - players
   - camera angles
   - singles/doubles
   - indoor/outdoor lighting
   - YouTube editing styles

The first target is not perfect action classification. The first target is to reduce manual annotation time.

## Success Criteria

MVP success:

- User can import one YouTube match video.
- User can assign players for useful court segments.
- User can create and edit a per-player action timeline.
- Exported CSV/JSON is correct enough to inspect manually.
- Every correction is saved as structured training data.
- User can tell which ranges were reviewed, skipped, or still unreviewed.
- Every heavy processing result is tied to a job id and parameters.
- `metrics.json` and `project_summary.json` can be produced for one project.

Quality targets after MVP:

- Candidate hit-event recall above 80 percent on clear court segments.
- Manual correction time below real-time playback speed for familiar videos.
- Player identity does not silently switch without a low-confidence prompt.
- No model suggestion directly overwrites human-approved annotation data.

## Evaluation Harness

MVP metrics:

- `review_time_per_video`
- `annotations_per_minute`
- `candidate_event_recall_on_reviewed_segments`
- `false_positive_rate`
- `identity_corrections_count`
- `action_corrections_by_label`
- `reviewed_duration_ms`
- `skipped_non_game_duration_ms`
- `unreviewed_duration_ms`

Metrics must distinguish unavailable from zero. For example, recall over zero reviewed ranges is unavailable, not `0.0`.

## Processing and UI Boundary

Heavy processing must run through replayable jobs:

- video download
- metadata extraction
- pose extraction
- segment detection
- hit candidate generation
- clip extraction
- metrics generation

The Streamlit render loop may read cached artifacts and project state, write small annotation events, and update queue/coverage state. It must not recompute pose extraction or scan a full video on every UI rerun.
